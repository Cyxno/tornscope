# TornScope 2.0 Architecture

How 2.0 is built: from recording history to acting on it, without new
infrastructure, new Torn API calls, or a second anything.

## Design constraints (held)

1. **Zero new Torn API calls.** Every 2.0 figure derives from stored snapshots
   and events. The only live data reused is `/api/today`'s existing 30s-cache
   (which already owned live-state freshness in 1.0).
2. **One additive migration.** The only schema change is the `Goal` table —
   user intent (metric/target/date/status), never derived data. Expand-only;
   1.0.x never reads it, so rollback needs no data migration.
3. **One implementation per concept.** Fact gathering lives once in
   `@tornscope/database` (`repositories/intelligence-facts.ts`); the API and
   the worker's notification producers both call it. Session inference stays
   single-sourced in `@tornscope/analytics/progression.ts` (evidence shaping is
   promoted there as `shapeEnergyInputs`).
4. **Pure analytics.** Projections, insights, training/economy intelligence and
   the freshness/action derivations are pure functions with explicit
   confidence, provenance and policy constants. Same conventions as 1.0
   (`exact | derived | estimated`, plus `inferred` where session-derived).

## Honesty rules (enforced by tests)

- **Projections**: an ETA requires ≥4 points spanning ≥3 days, median and
  least-squares slopes agreeing in sign and magnitude (≤50% divergence), and
  R² ≥ 0.3. Low confidence → `too_volatile`, no ETA. Beyond 5 years → withheld.
  Velocity is the median of interpolated per-day deltas — one lucky day cannot
  promise a date. Wealth ETAs past one year degrade in confidence.
- **Battle-stat projections** use the EMPIRICAL `relative_compounding`
  model (semantic audit: linear gain/day is the WRONG shape when gains move
  with the stat): calibrated on the player's observed relative growth and
  simulated iteratively forward. It is an EMPIRICAL projection, not a
  mechanistic simulator: recent_conditions_assumed, confidence capped at
  medium (perfect fit ≠ trustworthy forecast), always a range, level
  withheld entirely (`mechanics_not_modelled`). Taxonomy + full spec:
  `docs/SEMANTIC-AUDIT-2.0.md`.
- **Insights**: each rule gates on minimum sample size and a relative-shift
  floor (25% default; training 12%; energy-at-cap 50%) and absolute money
  floors. dedupeKeys are period-anchored (week/month buckets) so the same
  finding cannot re-fire daily. Feed capped at 8, one per kind.
- **Freshness**: `failed` only when the last attempt failed AND the stored data
  is past fresh age (a failing sync with fresh data reads `delayed`, never
  `fresh`); capability-denied and never-attempted read `unavailable`; live
  domains (stocks/merits) never pretend to have cursors.
- **Command center**: `critical` is reserved; insights never outrank real
  actions; data-health items only exist for profiles with a credential; all
  live-derived items require a fresh today payload (≤15 min).

## Performance

- API: two new caches (insights 120s, command center 20s per profile); the
  heaviest query path (training-session inference) runs inside the cached
  insights build only.
- Worker: goal/OC producers are a handful of indexed reads inside the existing
  120s-throttled notification cycle; the insight producer is daily and
  opt-in. No new queues, no new intervals, no Torn requests.
- Demo: goals seed with the profile; the routine top-up does not touch goals
  (their progress reads snapshots, which the top-up already extends).
