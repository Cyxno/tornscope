state and preferences. Performed on an **isolated restore** of the actual
production database — production was never modified.

## 20. Rollback reality (Part 59)

- v0.1 application code CANNOT run against the v0.2 schema without issues
  (v0.2 adds tables/columns v0.1 ignores — v0.1 would run, but any v0.2-era
  rows it is unaware of, e.g. bars snapshots and notification events, would
  be invisible to it; Prisma-version drift makes this unsupported).
- Therefore the supported rollback is: restore the pre-upgrade database
  backup (procedure proven below) and redeploy the v0.1 images.
- Data written after the upgrade and before a rollback restore would be lost
  (standard restore semantics). The backup must be taken immediately before
  promotion.

## 21. Backup / restore procedure (Parts 60–61)

Proven sequence (executed in this rehearsal against production, minus the
promote step):

```bash
# 1. Record state
cd /workspace/tornscope && git rev-parse HEAD   # record SHA
docker exec tornscope-postgres-1 psql -U tornscope -d tornscope \
  -c "SELECT migration_name FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 1"
# 2. Dump (read-only, consistent snapshot; production stays up)
docker exec tornscope-postgres-1 pg_dump -U tornscope -d tornscope \
  > /mnt/user/appdata/tornscope/backup-v0.1-final.sql
sha256sum /mnt/user/appdata/tornscope/backup-v0.1-final.sql
# 3. Verify restorability (isolated target)
docker run -d --name tornscope-restore-check -e POSTGRES_USER=tornscope \
  -e POSTGRES_PASSWORD=<throwaway> -e POSTGRES_DB=tornscope \
  -p 127.0.0.1:55433:5432 postgres:16-alpine
docker exec -i tornscope-restore-check psql -U tornscope -d tornscope \
  < /mnt/user/appdata/tornscope/backup-v0.1-final.sql
docker exec tornscope-restore-check psql -U tornscope -d tornscope \
  -c "SELECT count(*) FROM _prisma_migrations"   # must equal source
# 4. Promote (separate task): scripts/deploy-prod.sh
# 5. Rollback if needed: stop stack, drop/recreate DB, restore dump,
#    checkout previous main SHA, deploy-prod.sh
```

## 22. Known risks

1. `prisma migrate deploy` creates a missing target database instead of
   failing; production compose passes the exact configured name and the
   migrate service runs before api/worker can start, so a typo surfaces as a
   failed boot rather than data damage.
2. The rehearsal ran on the same host as production — isolation was by
   container, port binding and credentials, not by machine.
3. Upgrade downtime equals the restart window (build + migrate + boot;
   measured well under a minute on the rehearsal copy for migration).
