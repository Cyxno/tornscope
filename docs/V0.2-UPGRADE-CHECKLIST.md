# v0.2 production upgrade checklist

The operator-facing runbook for promoting `develop` → `main` → production.
Everything here was rehearsed on 2026-09-10 against a copy of the real
production database (see docs/DATABASE-MIGRATIONS.md, "v0.2 migration
inventory"). Do not skip steps; check boxes in order.

## BEFORE RELEASE

- [ ] CI green on `develop` (lint, typecheck, svelte-check, unit suites, build)
- [ ] Full test suite green locally: `pnpm test` (DB-backed suites included)
- [ ] Fresh production backup taken:
      `docker exec tornscope-postgres-1 pg_dump -U tornscope -d tornscope -Fc > /mnt/user/backups/tornscope/tornscope-pre-$(date +%Y%m%d-%H%M%S).dump`
- [ ] Backup integrity verified (`pg_restore --list` on the dump; size sane)
- [ ] Migration rehearsal succeeded on this exact release candidate:
      `scripts/rehearse-prod-upgrade.sh --from-prod` (optionally `START_API=1`)
      - migrations apply cleanly to a copy of production
      - row-count diff shows no data loss (bookkeeping rows aside)
      - second `migrate deploy` reports "No pending migrations" (idempotent)
      - with `START_API=1`: DB + Redis "ok" on the upgraded copy
        (a `worker: stale` readiness warning is expected — no worker runs in
        the rehearsal environment; it is not a migration failure)
- [ ] Migration inventory reviewed: docs/DATABASE-MIGRATIONS.md, "v0.2
      migration inventory" — every pending migration classified SAFE EXPAND
      or explicitly allow-listed with a compatibility plan
- [ ] No destructive operation without a documented compatibility plan
      (enforced by `packages/database/tests/migration-safety.test.ts`)
- [ ] Clean install verified: empty database → all migrations → `prisma
      validate` passes (CI proves this on every push; the migration-safety
      test re-proves it against a throwaway DB when `TEST_DATABASE_URL` is set)
- [ ] Current-production → v0.2 upgrade verified by the rehearsal above
      (both paths are mandatory; one is not a substitute for the other)

## DEPLOY (maintenance window: minutes)

1. [ ] Confirm the exact release SHA; production checkout on `main` at that
      SHA, clean tree, in sync with origin (`deploy-prod.sh` enforces this)
2. [ ] Take the final pre-migration backup (step above) — this is the
      rollback artifact; keep it until the next scheduled backup succeeds
3. [ ] Run the deploy: `scripts/deploy-prod.sh` (builds, runs the migrate
      one-shot via the migrator container, then restarts services)
4. [ ] Verify the migrate one-shot exited 0:
      `docker logs tornscope-migrate-1` (or `docker ps -a | grep migrate`)
5. [ ] Verify containers: web healthy, api healthy, worker running,
      postgres healthy, redis healthy
6. [ ] `curl http://127.0.0.1:3100/api/health` → `{"status":"ok"}`
7. [ ] `curl http://127.0.0.1:3100/api/ready` → `{"status":"ready",...}`
8. [ ] Confirm the reported build SHA matches the release SHA
9. [ ] Sync states: check Sync Status — no resource stuck in an unexpected
      state; capability-denied resources still parked with retained history

## AFTER

- [ ] Core pages render (Overview, Today, Economy, Drugs, Travel, Timeline,
      Sync Status, Settings) with a real profile
- [ ] Row counts sane vs the pre-deploy backup (spot query or the rehearsal
      script's counting method)
- [ ] New `SyncState.lastErrorKind` column exists and is NULL for old rows
      until they next run (expected)
- [ ] No error spike in container logs over the first sync cycle
- [ ] Retain the pre-deploy backup per the backup schedule

## ROLLBACK / RECOVERY

Decision points:

- **Migrate succeeded, app failed to start** → do NOT restore the backup.
  The schema change is expand-only and backward-compatible in shape; fix the
  app (rollback the release SHA if needed — the 0.1.x app runs fine against
  the expanded schema) and redeploy.
- **Worker failing after upgrade** → the migration is not the suspect (it
  adds a nullable column); roll back the release SHA first, investigate
  after. Collected data is unaffected.
- **Migrate interrupted mid-run** → Prisma records applied migrations
  transactionally per migration. Re-run `prisma migrate deploy` (the migrate
  one-shot runs on `up`); it resumes from the last completed migration. If
  it cannot, restore the backup and re-run the whole deploy.
- **Genuine data corruption suspected** → stop the stack, restore the
  pre-deploy backup into a scratch database first, verify, then restore into
  production. Never hand-edit `_prisma_migrations` casually; a restore
  re-imports the migration table state as it was.

Principles: backups before upgrades; migrations are forward-only; restore
only when genuinely necessary; the rehearsal script is the same restore path
used for real recovery, so it doubles as a restore drill.
